# C++26 Feature Baseline

Every entry below was established by compiling and running code on this machine,
not from documentation. Where a feature is unavailable, the measured reason is
given, because "not supported" and "not supported *here, for this reason*" lead
to different decisions.

Measured on:

```
GCC 16.1.0 (Homebrew), libstdc++ 20260430, aarch64-apple-darwin25
CMake 4.4.1, Ninja 1.13.2, __cplusplus = 202400
```

## 2. Contracts

Used through standard syntax with **no project wrapper**: no macro facade, and no
replacement violation handler. GCC's standard handler already reports everything
an operator needs:

```
contract violation in function void openproof::foundation::secureWipe(void*, std::size_t)
  at src/foundation/secret.cpp:17: size == 0U || data != nullptr
[assertion_kind: assert, semantic: enforce, mode: predicate_false, terminating: yes]
```

### Build flags

`-fcontracts` is passed at **compile and link** time, and
`-fcontract-evaluation-semantic=enforce` at compile time.

The link flag is not optional. Passing `-fcontracts` only to the compiler
produces an undefined reference to `handle_contract_violation`, which looks like
a missing user-supplied handler and is not one — it is a missing link flag. That
misreading is what originally led this project to write a custom handler it did
not need.

`OPENPROOF_CONTRACT_SEMANTIC` selects the semantic (`ignore`, `observe`, `enforce`,
`quick_enforce`); it defaults to `enforce` and is recorded in the startup log,
because `observe` does not stop a process whose invariants have broken.

### What may be checked by a contract

A contract states an invariant **the platform's own code** must uphold. Untrusted
input is never checked with a contract — a malformed token, a bad configuration
file or a hostile request body returns a `Result`.

This is a security requirement, not a style rule: under `enforce` a violated
contract terminates the process, so a contract guarding attacker-controlled input
would be a remote shutdown.

### Placement rule (GCC 16.1.0 defect)

Contracts and modules interact badly in one specific way, and **the failure is
silent**:

| Placement | Behaviour |
|---|---|
| `pre`/`post` on a function *defined* in the `.cppm` | emits an undefined `__tu_has_violation` into every consumer |
| `pre`/`post` on a declaration whose definition is out-of-line in a `.cpp` | **silently not enforced** |
| `pre`/`post` added on the out-of-line definition | hard error: "declaration adds contracts" |
| `contract_assert` in a body in a `.cpp` module unit | **works** |

Only the last row is usable. The project therefore states preconditions as
Doxygen `@pre` on the declaration and enforces them with `contract_assert` as the
first statement of the definition. Invariants that would naturally be a `post` on
an exported inline function are covered by unit tests instead, with a comment at
the site saying so.

Reduced case for the silent row:

```cpp
// m.cppm
export void wipe(void*, const std::size_t n) noexcept pre (n == 0 || p != nullptr);
// m.cpp
module m;  void wipe(void*, const std::size_t) noexcept { }
// caller: wipe(nullptr, 16) prints "SURVIVED" -- no check, no diagnostic
```

## 3. Reflection — available but blocked

Reflection **works** on this compiler. This runs and prints `NOT_FOUND`:

```cpp
consteval std::string_view nameOf(ErrorCode code) {
    template for (constexpr auto e :
                  std::define_static_array(std::meta::enumerators_of(^^ErrorCode))) {
        if ([:e:] == code) { return std::meta::identifier_of(e); }
    }
    return "UNKNOWN";
}
```

It is nonetheless **not enabled**, because `-freflection` breaks this project's
module build. Reduced case — no reflection used anywhere, zero errors without the
flag, six with it:

```cpp
module;  #include <string>
export module part.m:error;      // partition A

module;  #include <expected>
export module part.m:result;     // partition B
import :error;                   // fails only when -freflection is on
```

```
error: conflicting imported declaration 'typedef union __mbstate_t __mbstate_t'
error: conflicting imported declaration 'typedef class std::fpos<__mbstate_t> std::streampos'
```

`openproof.foundation`, `openproof.observability`, `openproof.security`, `openproof.policy` and
`openproof.identity.provider` are all built from partitions, so the flag breaks the
build globally. Enabling it for a subset of targets would compile the codebase
two different ways, which is worse than not using it.

**Intended use once fixed.** Five hand-written enum-to-string functions
(`errorCodeName`, `logLevelName`, `assuranceLevelName`, `providerKindName`,
`claimNameKey`) would be generated from `enumerators_of`, making "added an
enumerator, forgot its wire name" impossible. Nothing in the source depends on
reflection today, so adopting it is a flag plus that rewrite.

Note the wire names are a compatibility contract: `ProviderKind::OAuth2` must
serialize as `oauth2`, which no mechanical case transform produces. The rewrite
would generate names *and* keep an explicit exception table, not blindly rename.

## 4. `std::simd` — x86 only

The `<simd>` header exists, but its contents are gated in `bits/version.h`:

```cpp
#if (__cplusplus > 202302L) && _GLIBCXX_HOSTED
    && (__cpp_structured_bindings >= 202411L && __cpp_expansion_statements >= 202411L
        && __SSE2__)
#  define __glibcxx_simd 202506L
```

`__SSE2__` is never defined on aarch64, so `std::simd` does not exist on this
machine. `std::experimental::simd` does work (`native_simd<float>::size() == 4`),
though `reduce()` hits a libstdc++ NEON bug.

No SIMD is used in Phase 1. The candidate hot paths are hex and base64url
encoding for tokens, and optimising them before the gateway exists and before any
measurement would be speculative.

## 5. `import std;` — unavailable

Requested, and genuinely not possible here. Homebrew's GCC 16 ships the module
manifest but the sources are **1-byte stubs**:

```
$ wc -c /opt/homebrew/Cellar/gcc/16.1.0/include/c++/16/bits/std.cc
       1
```

`libstdc++.modules.json` points at that stub, so CMake's `CXX_MODULE_STD` fails
with "does not provide a module interface unit or partition".

LLVM 22 *does* ship a real `std.cppm`, so `import std;` is achievable on Clang —
but Clang 22 implements neither contracts nor reflection nor `#embed` nor
`std::text_encoding`, so that trade was declined. Standard headers therefore
appear in each module's global module fragment.

## 6. Available but deliberately unused

Listing these so their absence reads as a decision rather than an oversight.

- **`std::generator` / coroutines.** The natural use is async I/O in the OpenProof gateway
  (Phase 5). The one Phase 1 candidate — streaming repository keys — would hold a
  mutex across a suspension point, which is a deadlock waiting to happen.
- **`std::indirect` / `std::polymorphic`.** These give *value* semantics to
  polymorphic or incomplete members. `ProviderRegistry` deliberately has
  *reference* semantics and owns providers via `unique_ptr`; using
  `std::polymorphic` there would deep-copy providers, which is wrong. The real
  fit is the recursive ABAC policy expression tree in Phase 4, where
  `std::indirect` is the natural way to hold a recursive value type.
- **`std::mdspan`.** No multidimensional data exists in an identity domain.

---

## 7. Toolchain requirement

**GCC 16 or newer is required.** Clang is rejected at configure time with a
diagnostic naming the missing features. This is a change from Phase 1, which
supported both: contracts and reflection are used through standard syntax, and
wrapping them in portability macros to accommodate a compiler that lacks them
would put a project-specific facade in front of standard language features —
exactly what this project should not do.

Portability returns when Clang and MSVC implement P2900.
